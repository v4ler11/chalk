# Chalk

A desktop chat client for any OpenAI-compatible API, built with Tauri 2 (Rust backend) + React + TypeScript + Vite.

The interface follows the design the app was built from: a frameless window whose chrome is drawn in the webview, a channel of threads, a serif reading column for the transcript, and a rounded composer card.

- Chat history in SQLite: one row per chat, holding the whole transcript as JSON — the same array the UI holds, its timing keys and the provider-shaped payloads included — in `chats.db` in the OS app-data directory. The channel lists the threads oldest first, read in stretches — today, yesterday, this week, this month, then by the month they were in — each opened by a divider naming it; a row opens its thread on a click, and deletes it after asking, from the button that appears under the pointer. The most recently written chat is reopened at launch.
- A chat enters the history with its first message, so a prompt typed in the channel is a draft with no row of its own until it is sent, and is written again as each message settles: a reload, a crash, or a quit mid-answer keeps everything up to the last message. A chat is named after its first prompt. Writing is chained, since a transcript is stored whole and an older write landing last would put the older transcript back.
- A system prompt can be set in the settings window. It is prepended to every request as a `system` message there, in the backend, rather than held by the window: a chat's transcript never carries it, and changing it applies from the next request on. What the app itself has to say goes under it — the note about the header every prompt carries — so a request whose prompt is empty still has that much to say. The prompt may hold `@{{TODAY}}`, which is replaced on each send with that send's date and time in the user's own time zone — `Fri 2 Oct 2026 20:39:02`; a name the app does not know is left as written rather than being eaten. Worth knowing: a token that resolves to the second is a different prefix on every request, and a provider's prompt cache is a prefix cache — the time of a send is what each prompt's own header is for, so `@{{TODAY}}` is better left out of the system prompt. The file keeps the prompt as written, so whatever is in it stays live. Nothing searches the history yet. Token counts and price are kept with the answer they were reported for, so a transcript carries them back with it.
- **Every prompt is sent with a header the client writes**: the date and time it was sent, and how long after the previous one — `Sun 4 Oct 2026 20:39:02 · 12m since the previous message` — then a line of three dashes, then what the user typed. The moment is kept with the message, so the header is written once and written the same on every later request that carries it, and the transcript holds the user's own words throughout: an edit hands those back to the composer, with no header to delete. What the model is told about it is a note in the system prompt, since a model that took the time for something the user typed would have been misled by the app. This is also what leaves a conversation cacheable: a provider's prompt cache is a prefix cache, so a header that shifted with the clock would make every request a different prefix and nothing would ever be reused.
- Frameless window (`decorations: false`), transparent so its corners are the app's own (`border-radius`) rather than the OS's. The window is a row: the sidebar's own column on the left, and the panes taking everything else. The sidebar is narrow and always there, since a thread is opened *in* the channel rather than instead of it, and its head is the window's chrome — the traffic lights, which drive the real window, and the drag region — so the column and the lights are one surface. The panes share one box beside it, and are read in layers: the pane the column's top rows hold — the channel's feed, or the pins — then a thread over it, then the settings or the JSON view, which stand in for the chat. Each layer draws its own head at its own top edge: a strip that drags the window and holds what belongs to that pane — the way back into the feed while a thread is open, and the dots over the switches — and, when the JSON view stands in for the chat, a bar under it naming it and holding the way out. The sidebar's head and the strips are drag regions, so a press anywhere along the top moves the window and a double-click maximizes, while the controls and the model chip keep their own clicks. A thread's pane is drawn over the pane beneath, which stays mounted under it, so opening a thread and coming back rebuilds neither the feed nor its scroll — and leaves the sidebar's row where it was, so a thread opened from the pins comes back to the pins.
- The thread's pane slides in over the channel when a thread opens and back out when the channel is the view again, and the channel stays mounted under it either way, so its scroll and its half-typed draft survive the trip.
- **The sidebar is the window's own column**, and holds three rows: **Channel**, the feed of threads, and **Pins**, everything pinned out of it, one under the other at its head, and **Settings** at its foot, apart from the two since it is the one that is not a place the chat is in. What the window can show is one list, so a pane is opened from the row that stands for it, and the settings are no exception: their row in the column opens them and leaves them, rather than an item of the nav's menu doing it at one remove. The pins take the pane the way the channel does — the same strip at the top, then the list: a tab is not a mode, so nothing names it and nothing offers a way out of it, since the sidebar's own row already does both. The list is the channel's own rows with the unpinned ones left out, drawn by the channel's own component: the same face, the same prompt with its pictures, the same line under it, and the same pill at the corner. All the list adds is its order: most recently pinned first, rather than oldest posted. It draws none of the pin's own marks — every row here is pinned and the pane says so — so the pill, which is how a pin comes off, is the one thing it repeats from the channel. Nothing is pushed to it: a pin is the window's own record, so the list is read when it is drawn and again after anything that changes what is pinned.
- Every row of the feed is one thread as a channel draws a message: the face of whoever posted it, their name and when they posted it, what they asked as it was typed, cut at three lines with the rest waiting in the thread the row opens, and, under it, who answered — the person's own circle once they have answered, the assistant's, the count of what was said, and when it last was.
- The composer and the transcript share one measure: a share of the window width (`72vw`), capped at `1120px`, so both grow with the window and stay in step. They also take it out of the same padding, so the composer's edges meet the message column's at every width, and both are centred on the pane they stand in. The composer's own parts — the draft's type, its padding, the paperclip, the send button — grow with it, so a wide window gets a composer in proportion rather than a small one adrift in a wide bar.
- The model in use is named at the right of the chat panel's nav, with a chevron: clicking it opens the list of models, the one in use marked. A chat holds its own model: choosing one here saves it with that chat, and the next new chat takes up the model the most recently written chat was holding, or the head of the list when the history has nothing to say. A row written before chats had models counts as having nothing to say, so it inherits the head of the list and keeps it from then on. The name is shown whole.
- The three-dots at the right of a thread's bar opens the switches a thread has, and a bar belonging to anything else carries no menu rather than a menu with nothing in it. **JSON view** stands in for the transcript and the composer in the settings' own shape — the strip at the top, then sections down the left of the pane — and it is the one pane that also wears a bar: nothing in the column stands for it, so the bar names it and holds the red **ESC** that leaves the view at the bar's right (the Escape key presses it too). The pane is the request rather than the window's copy of it — **History** is the messages the backend assembles for the request, so the configured prompt arrives resolved, with the lazily imported servers named under it, and the timings and usage the window keeps are left out because the model is never sent them; **Tools** is the request's own tool list, grouped by the server that offers it — the app's own `load_lazy_mcp` first, offered for as long as this chat calls a lazily imported server at all — loaded or not, since the load is one-way and asking again is answered rather than unknown — each group collapsed by default and headed by how many tools it holds and what they cost a request (`11 tools ~4.3k Tok`, a token being about a quarter of the JSON sent), so a lazily imported server that has not been loaded is absent from it and appears instead as the prompt's addendum in **History** — and a **Copy** button holds the pane's bottom-right corner whatever the JSON is doing under it. The pane stays where it is, so a chat opened from the channel while the view is on shows its JSON. The view and its tab are the window's rather than any chat's: they stay on while chats are opened, until the escape button or the menu is pressed.
- The send button holds its place whether or not there is a draft; an empty one sends nothing.
- What the chat has cost sits beside the send button: every answer's price, summed, written as money with two decimals — `$0.00`. The total is the transcript's own, summed from what each answer reported, so a chat read back from the history shows what it cost and nothing has to be kept twice, and a provider that reports no prices shows nothing at all. The answers here cost fractions of a cent, so a chat reads `$0.00` until its spend passes half a cent.
- **OpenRouter's response cache is asked for on every request** while OpenRouter is the provider: the same request made twice — same model, same body, same key — is answered from OpenRouter's own cache the second time if it is made within five minutes, without reaching a model at all, so it is free and immediate. Every response comes back with the gateway's own verdict on it, which is kept with the answer it belongs to, so a cached one says so wherever it is read. Nothing of this goes anywhere else: a custom endpoint knows nothing of that header, and the app sends it nowhere else. Two caches are at work and they are different things: this one replays an answer whole, while the provider's own prompt cache keeps the prefix of a conversation — which the app asks no permission to use, only brings the stable prefix it needs, and reads back as a cache hit rate beside every answer's tokens. Each conversation is pinned to a single upstream with the session key OpenRouter's sticky routing takes, so the provider holding the cache is the one asked again: without that pin, routing only sticks once a hit has already happened. Providers differ in what they need, though, and the app sends what the strictest of them do: the last block of text in the request is marked with a `cache_control` breakpoint, because Gemini and Anthropic — through OpenRouter — cache nothing at all without one, while DeepSeek, OpenAI, Grok, Moonshot and Groq work the prefix out for themselves and ignore the mark. Gemini has a second rule: it writes no cache under a few thousand tokens, so a short Gemini conversation reads no cache however it is asked, while the same conversation on DeepSeek reads its share from the first turn. The two also count differently — OpenRouter hands back Gemini's prompt count with the cached tokens already added to it, so a Gemini request cached through and through reads about 50%. The rate shown is the gateway's own arithmetic on its own counters, not the app's.
- The reasoning level is chosen next to the paperclip, from **off, low, med, high**: the brain alone, in the tools' own grey, while nothing is being asked for — a click takes up `med` and turns it into a pill — and a pill of two buttons while a level is in force: the brain gives the level up, and the level's own letter and chevron open the menu, which holds off as well. Each control names itself under the pointer, the way the rail's buttons do: **Attach files** on the paperclip, **Reasoning** on the brain. The menu is drawn at the window's edge rather than in the card, whose bar clips whatever would hang out of it. The level rides with the request as the gateways' unified `reasoning.effort`, spelled out in full (`med` is `medium`), and off asks for `none` — how a model that reasons by default is told not to; a model whose reasoning is mandatory answers that with an error rather than quietly thinking. Like the model, the level belongs to the chat, is saved with it, and the next new chat takes up the level the most recently written chat was holding.
- Which model context protocol servers the chat calls is chosen beside the reasoning control, in that control's own shape and blue: the hammer alone while it calls none — and then the hammer is what opens the list, there being no other way to switch one back on — and, while it calls any, a pill of the hammer and the number of servers it calls. In that pill the hammer gives them all up and the number, with its chevron, opens the list. The list holds the servers the settings window has enabled, each with a switch that decides whether *this* conversation is sent with it, and, under its name, how many tools it offers and what they cost a request — `11 tools ~4.3k Tok`, a quarter of the JSON they are sent as, counted in the backend off the very bytes the request is charged for; a server imported lazily says `lazy` there instead — italic, and in the composer's own blue — until this chat loads it, and its count and its price from then on, like any other server's; a server that cannot be reached says so in place of both, in red, and **Refresh tools** asks them all again — connecting afresh, which is the only way to see a tool a server has grown since the window was opened. There is deliberately no way into the settings from here: what a server *is* belongs there, whether this chat calls it belongs here. The choice is saved with the chat the way its model is, so a conversation picked up again calls what it called, a new chat takes up the last one's — and every row written before there was a control for it has never chosen, which is taken as calling every enabled server.
- A tool call is one row of the transcript rather than two — and the rows of a turn are held close together and close to what they belong to, a run of them reading as one stretch of work rather than a stack of replies: how long the server took, what was called, and the arguments as they were sent, on a single line, cut off rather than wrapped — in the monospace face, since it is a record of an identifier being invoked. Under the pointer, or with the caret in it, the row takes the transcript's tint, its text comes up to the reading colour, and the chevron onto its card appears. Clicking it opens that card: the server's chip and the tool, then **Arguments** and **Result**, each laid out from its JSON where it is JSON. A call and the tool message that answered it are the same fact, so they are drawn as one — paired by the id the message carries, the row read from the message that asked, since that is where the name and the arguments are written — and a call nothing has answered yet (running, or waiting on the approval card) shows its arguments alone. The timer is the server's own time, from asking to answering: `412ms`, `0.4s`, `1:02.3`, and blank on a call that never ran — one declined, or one written before the app timed them.
- Images can be attached to a prompt: pasted into the composer, or picked through the paperclip, which opens the file panel. Each arrives as a square above the draft, drawn at once from the file and taken away again by the × at its top-right; the row scrolls sideways once there are more than fit. While an image is being prepared — decoded, and scaled down and re-encoded when it is larger than a provider comfortably takes (longest side `1600px`, JPEG) — a spinner sits over it and the send is held back, so a request never goes out missing its picture. The image rides with the prompt as an `image_url` part of its content, is drawn back in the transcript, and is kept when the answer is asked again.
- The window has no menu bar, so its commands are bound in the webview and each shortcut is shown where its command lives: `⌘,` for the settings, named on the column's row for them, and `⌘J` for the JSON view, named on the row the nav's three-dots menu holds, Escape for the way back out of whatever the pane is showing, and `⌘+Enter` to send, which the composer's placeholder says — Enter there is a newline, like any other editor's. Posting from the channel leaves the caret in the composer, so the next request can be typed without reaching for the mouse. Control stands in for Command off a Mac.
- Token-streamed assistant responses rendered as Markdown (GFM) — progressively, block by block, so each settled block is parsed once and never re-rendered. The live answer and the settled one are laid out from the same tree, so a message does not shift the moment the response ends.
- Math in answers is typeset by KaTeX: `$x^2$` inline, and `$$ … $$` with the fences on their own lines for display. A formula wider than the bubble scrolls inside it, like a table.
- Your own prompts render as plain text, exactly as typed — markdown in a prompt is text, not formatting — and each is ruled off by one hand-drawn wavy line: irregular humps along a single path, so it never breaks at a repeat.
- **A thread's row in the channel offers two things under the pointer**, in a floating pill at its own top-right corner: pin the thread, or delete it. It is out of the flow, since that corner is empty — the face and the words are at the row's left — so the feed is the same height whether or not it is drawn. Pin marks the thread and the pill's icon becomes the unpin; delete asks first, twice over: the bin becomes Delete and Cancel in the pill, and the row says the same thing in its own words where the prompt was, so the row about to go is the one asking. A pinned row is drawn as a block of its own — a warm ground, a rule down its left edge, and the pin on the line its name is on — and its padding gives back what the rule takes, so every row's face, name and words stay on one column. Nothing about a row moves when it is pinned: the mark goes on a line that was already there, and the line under the prompt is held open whether or not it has anything to say, so a thread's first answer landing does not grow its row and push the ones under it down. The pin itself is a column of the row rather than part of the transcript, written on its own, so pinning a thread that is answering is not undone by what its run writes next; nothing else about the chat moves, least of all the moment it was last answered.
- A prompt under the pointer offers three things beneath it, in the gap the transcript already leaves: copy the message (the icon becomes a check for a moment), ask for the answer again, or rewrite it. None of them are offered while an answer is arriving, and the row holds no space, so the transcript never moves under the pointer. Regenerating and sending a rewrite both cut the transcript back to that prompt and start the conversation over from there: every message after it is dropped, the ones before it are untouched, and the history is rewritten the same way. Rewriting puts the message in the composer, under a line that says so and the × that gives the edit up — putting back whatever draft it displaced.
- An answer under the pointer offers its own two things in the same row beneath it, hung from the answer's own left edge the way a prompt's hang from the right: copy the message — the icon becoming a check for a moment — and, where the provider reported them, the tokens the answer used, how much of what was sent it had already cached, and what it cost. Those are a tip over the icon rather than a click: the icon is what there is to hover, and it is read, not pressed. The report arrives on the stream's last frame and is kept with the answer, so a chat read back from the history still shows it; an answer written before the app kept it offers the copy alone. A response OpenRouter answered from its own cache reports no tokens and no price — every counter zeroed — so the tip names it rather than reading out the zeroes, and one whose model has no prompt cache shows no rate at all rather than a rate of nothing.
- Every answer opens with a status line: how long the model took to produce anything at all, and — only when it reasoned at all — how long it spent thinking, with a chevron onto that reasoning, both on the one line. A model that thought nothing shows the wait alone, with no zero to read and nothing to open. A turn that called tools went round several times, and what every round reasoned is gathered onto the message that answers for them — one block, its timers summed, since between them they are what the turn took — so a round that only asked for tools is left showing its call rows and nothing above them. The reasoning opens below that line, so the line under your pointer never moves, and the chevron turns down onto what it opens. The block is shut until you open it and nothing remembers your choice, so a block never opens or shuts under your hands. The line and the reasoning are chrome: neither can be selected by dragging, while the answer itself still can.
- Durations read to a tenth of a second: `0.4s`, then `12.8s`, then `1:23.4`. The wait and the thinking each carry their own.
- The transcript follows new output: while an answer streams the view is held at the lowest scroll point there is, so the newest line is the last one on screen and the only space under it is the transcript's own padding. A new message re-attaches it whatever the reader was doing — a send, or a message that arrives while nothing is streaming — since what is new is new and it is waiting at the end; scrolling up otherwise releases the follow and leaves the view where it was put, even as tokens keep arriving, and the answer landing at the end of that stream does not pull it back.
- Scrolling up holds your position for as long as you read — even while tokens keep arriving — and a floating ↓ button (or scrolling back to the bottom, or sending) re-attaches.
- **Settings take the chat's place in the window** (the **Settings** row at the foot of the column, or `⌘,`), named by that row and left by it too, since a pane of the column is a pane the column names: the pane is the strip, then a vertical list of sections down the left — **General**, **Customization**, **MCP**, then the Logs row at its foot — opens one page beside it. Pressing Escape, opening a chat from the history, or starting a new chat puts them away again. General holds the runtime-editable provider — the selector's two, **OpenRouter** or **Custom**, the latter with the endpoint it names — the bearer key, and the models — a list, added to and removed from a row at a time, that cannot be emptied. Customization holds the system prompt, one textarea, sent ahead of every request and never saved with a chat — the app's own note about the header each prompt carries goes under it, which is why a request carries a system message even when that box is empty. All five live in `~/.chalk/settings.yaml`: plaintext, and the config rather than a cache of it, so editing the file by hand is enough and editing it in the form rewrites the file there and then. The list's order is the picker's order, and its first entry is what a chat starts from when the history has nothing to say; a file still holding the single `model` key this settings file began with reads as a list of one, and a row left blank is not a model — it is dropped when the file is read. `provider` is one of two names — `openrouter`, or `custom`, which sends to the `endpoint` beside it — and a file written the old way, naming a gateway or spelling the endpoint out, is read into that pair: a name this app then knew — `openai`, `deepseek`, `groq`, `ollama`, `lmstudio` — becomes the endpoint it stood for, and OpenRouter's own URL is read as OpenRouter, which is what asks for its cache. Any OpenAI-compatible service works without the list growing. The file is generated rather than hand-maintained: a rewrite keeps its five keys and drops comments and anything else in it. The first run after the move carries over whatever `config.json` in the OS app-config directory held, so the key already in use is not lost to it. Saving updates the model chip. The API key is shown while the field has the caret and masked the rest of the time — its first five characters, then one asterisk per character after them — so it can be read and corrected in place, while a glance at an unfocused window, or a copy of the field, gives away nothing past the fifth. The button at the foot of the sections opens the log window.
- **Model context protocol servers** are configured in the settings' **MCP** page and kept in `~/.chalk/mcp.json`, beside the settings and as hand-editable: the file is the config rather than a cache of it, and it is kept to its owner's read, since a server's headers are where a key goes. A server is reached either by running a program and speaking the protocol over its standard streams (**stdio**) or by posting each message to a URL (**streamable HTTP**, with whatever headers the server needs); the page lists the servers, edits one at a time — type, name, id, url or command, headers or environment, and, for a server held back rather than offered, its **Import lazily** switch and the description the model reads in place of its tools — and can **Test** a server, saved or not, which connects, shows the revision that was agreed on, what the server calls itself, and the tools it offers. The id names the server in the names the model is given — `<id>__<tool>` — so it is held to one word. A server enters the list when it is saved, not when it is started on; a row is removed by the bin at its end, which asks the same question the history's rows ask, and the removal is written there and then. A server that is off is never started and its tools are never offered. What a request carries is the tools of the servers the *chat* calls — switched one at a time in the composer, and every enabled server until something is switched — and a call is carried out in the backend over the connection the app already holds; a server marked `"lazy": true` holds its tools back instead: they are not in the request at all, and what the model is given is its name, its `description` and the names of the tools it holds — no definitions, which is what the laziness is saving — in the system prompt under `Lazy Imported MCPs`, with a `load_lazy_mcp` tool to ask for the rest by. Calling that with a server's name puts its tools into the conversation like any other server's, and there they stay for the rest of the thread: the load is one-way, so a tool that has answered is never taken away under the model's hands; the result goes back as the `tool` message the conversation continues from. A server's tools run as the model asks for them unless the file says `"autoRun": false` on it — the one place that is decided, and never a control in the window — and then its calls stop above the composer until they are allowed or declined, either answer going back as the call's result. A tool the server itself declares read-only is the exception: it runs as the model asks either way, because the protocol's own hint says it changes nothing, so a round that only reads goes through while a round with a write in it stops. A file that does not mention the key at all runs them: the protocol asks hosts to obtain consent, and a server that is declared is taken as one its owner has decided about. One turn may go round for tools eight times before it is stopped — the calls of that last round are answered anyway, since a call left unanswered is one the provider refuses.
- **The app manages itself, too**: eight tools of its own ride with every request — `models_list`, `model_add`, `model_remove`, `mcp_list`, `mcp_add`, `mcp_update`, `mcp_remove`, `mcp_test`. They are offered the way a server's are and answered the way its settings window answers, and the JSON view groups them under **Chalk** beside the loader; what sets them apart is that no server is on them. They are in every request rather than a chat's choice — not something a chat can switch off — and they run as the model asks rather than stopping for an Allow, so what they did is a row of the transcript either way. What they write is exactly what the settings window writes: `settings.yaml` for the models and `mcp.json` for the servers, through the same save path, so a model that declares a server has it reachable on the next request and one that adds a model has it in the picker. The settings' own rules come with them: an id is added once, a place that is not there is refused, the last model cannot be removed, and a server is one word with something to reach it by. Two things they never touch — the API key, which would then be in the transcript and in the model's context, and the provider with its endpoint. A bearer token in a server's headers is named by its key and never by its value: `mcp_list` says which headers a server is reached with, not what is in them, so a listing can be read out loud.
- The protocol client speaks the two revisions this app is written for: `2026-07-28`, where there is no handshake at all and every request carries its own version, capabilities and identity, and `2025-11-25`, where a session is opened with an `initialize` first. A server is probed with the newer revision and falls back to the older one, so a server of either era works and the newer is used when both are on offer. The framing, the two transports and the negotiation are the reference Rust implementation's (`rmcp`), not this app's: what is here is the configuration, the connections, and the names the model sees. A server's own stderr is read into the log window, which is where a server that will not start says why.
- **The log is a window of its own** (Settings → the Logs row at its foot), declared in `tauri.conf.json` and rebuilt from that declaration if it has been closed, so it can be left open beside the chat. It shows the backend's entries, backfilled from `get_logs` and followed live over `app-log`, plus the log window's own console output; no other window's console is collected.
- All HTTP runs in the Rust backend via `reqwest`, and streaming is delivered to the webview over a Tauri `Channel`. The API key never reaches the webview, and there is no CORS involvement, so any OpenAI-compatible endpoint works.

Type is set in Space Grotesk (display), DM Sans (UI), and Newsreader (message text), bundled with the app so nothing is fetched at runtime. Both the light theme and the OS dark scheme are supported.

## Transparency and the App Store

A transparent window on macOS needs Tauri's `macos-private-api` feature (`Cargo.toml`) and `app.macOSPrivateApi` (`tauri.conf.json`). That is what makes the rounded corners possible, and it uses private APIs — **an App Store submission would have to drop the transparency**, and with it the rounded corners.

## Prerequisites

- Node.js (for npm)
- Rust (stable toolchain)
- macOS, Windows, or Linux desktop

## Run

```sh
npm install
npm run tauri dev
```

This starts Vite and compiles the Rust backend, then opens the desktop window.

Open **Settings** to edit the provider, API key, the list of models, or the system prompt — they are saved to `~/.chalk/settings.yaml` and apply from the next request on — and its **MCP** page to add model context protocol servers, which are saved to `~/.chalk/mcp.json`: either a program to run and speak to over its standard streams, or a URL to post to, with the headers it needs. Their tools are offered to the model and run as it asks for them; a server marked `"autoRun": false` in that file has its calls stop for you to allow instead, and one marked `"lazy": true` is not offered at all until the model loads it by name. The chat history is `chats.db` in the OS app-data directory; deleting it starts the history over, and the app runs without history at all if it cannot be opened.

Defaults point at OpenRouter: `provider: openrouter`, a list of one model, `deepseek/deepseek-v4.1-flash`, and no key — the app ships without one, so add yours in Settings or in the file before the first request. A file that names another gateway, or writes an endpoint out by hand, is read as `provider: custom` with that endpoint in `endpoint`, and saving from Settings writes the file the new way; OpenRouter's own URL written out is read as OpenRouter, since the name is what its cache hangs off.

## Build a release bundle

```sh
APPLE_SIGNING_IDENTITY="-" npm run tauri build -- --target aarch64-apple-darwin
```

The signing identity is not optional: without it the bundle carries only the
linker's ad-hoc signature and macOS reports it as damaged rather than as an
app from an unidentified developer. [`skills/RELEASE.md`](skills/RELEASE.md)
has the whole release — the version bump, the secret check, the artifact
verification, and the published dmg.
