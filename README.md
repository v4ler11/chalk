# Chalk

A desktop chat client for any OpenAI-compatible API, built with Tauri 2 (Rust backend) + React + TypeScript + Vite.

The interface follows the design the app was built from: a frameless window whose chrome is drawn in the webview, a channel of threads, a serif reading column for the transcript, and a rounded composer card.

- Chat history in SQLite: one row per chat, holding the whole transcript as JSON — the same array the UI holds, its timing keys and the provider-shaped payloads included — in `chats.db` in the OS app-data directory. The channel lists the threads oldest first, read in stretches — today, yesterday, this week, this month, then by the month they were in — each opened by a divider naming it; a row opens its thread on a click, and deletes it after asking, from the button that appears under the pointer. The most recently written chat is reopened at launch.
- A chat enters the history with its first message, so a prompt typed in the channel is a draft with no row of its own until it is sent, and is written again as each message settles: a reload, a crash, or a quit mid-answer keeps everything up to the last message. A chat is named after its first prompt. Writing is chained, since a transcript is stored whole and an older write landing last would put the older transcript back.
- A system prompt can be set in the settings window. It is prepended to every request as a `system` message there, in the backend, rather than held by the window: a chat's transcript never carries it, and changing it applies from the next request on. What the app itself has to say goes under it — the note about the header every prompt carries — so a request whose prompt is empty still has that much to say. The prompt may hold `@{{TODAY}}`, which is replaced on each send with that send's date and time in the user's own time zone — `Fri 2 Oct 2026 20:39:02`; a name the app does not know is left as written rather than being eaten. Worth knowing: a token that resolves to the second is a different prefix on every request, and a provider's prompt cache is a prefix cache — the time of a send is what each prompt's own header is for, so `@{{TODAY}}` is better left out of the system prompt. The file keeps the prompt as written, so whatever is in it stays live. Nothing searches the history yet. Token counts and price are kept with the answer they were reported for, so a transcript carries them back with it.
- **Every prompt is sent with a header the client writes**: the date and time it was sent, and how long after the previous one — `Sun 4 Oct 2026 20:39:02 · 12m since the previous message` — then a line of three dashes, then what the user typed. The moment is kept with the message, so the header is written once and written the same on every later request that carries it, and the transcript holds the user's own words throughout: an edit hands those back to the composer, with no header to delete. What the model is told about it is a note in the system prompt, since a model that took the time for something the user typed would have been misled by the app. This is also what leaves a conversation cacheable: a provider's prompt cache is a prefix cache, so a header that shifted with the clock would make every request a different prefix and nothing would ever be reused.
- Frameless window (`decorations: false`), transparent so its corners are the app's own (`border-radius`) rather than the OS's. The window is a row: the sidebar's own column on the left, and the panes taking everything else. The sidebar is narrow and always there, since a thread is opened *in* the channel rather than instead of it, and its head is the window's chrome — the traffic lights, which drive the real window, and the drag region — so the column and the lights are one surface. The panes share one box beside it, and are read in layers: the pane the column's top rows hold — the channel's feed, or the pins — then a thread over it, then the settings or the JSON view, which stand in for the chat. Each layer draws its own head at its own top edge: one strip that drags the window and holds what belongs to that pane — the way back into the feed while a thread is open, and the dots over the switches — and, on the panes that stand in for the chat, the mode's own name where the way back stands and its ESC at the far end, so a mode names itself on the head every pane already has rather than on a second one under it; a mode's strip carries neither the way back nor the dots, since both would answer questions the mode's own way out has already answered. The sidebar's head and the strips are drag regions, so a press anywhere along the top moves the window and a double-click maximizes, while the controls and the model chip keep their own clicks. A thread's pane is drawn over the pane beneath, which stays mounted under it, so opening a thread and coming back rebuilds neither the feed nor its scroll — and leaves the sidebar's row where it was, so a thread opened from the pins comes back to the pins.
- The thread's pane slides in over the channel when a thread opens and back out when the channel is the view again, and the channel stays mounted under it either way, so its scroll and its half-typed draft survive the trip.
- **The sidebar is the window's own column**, and holds three rows: **Channel**, the feed of threads, and **Pins**, everything pinned out of it, one under the other at its head, and **Settings** at its foot, apart from the two since it is the one that is not a place the chat is in. What the window can show is one list, so a pane is opened from the row that stands for it, and the settings are no exception: their row in the column opens them and leaves them, rather than an item of the nav's menu doing it at one remove. The pins take the pane the way the channel does — the same strip at the top, then the list: a tab is not a mode, so nothing names it and nothing offers a way out of it, since the sidebar's own row already does both — and it is the way back out of a thread opened from the list as well: pressing it again shows the pins, a thread being drawn over the pane the row holds rather than in place of it. The list is the channel's own rows with the unpinned ones left out, drawn by the channel's own component: the same face, the same prompt with its pictures, the same line under it, and the same pill at the corner. All the list adds is its order: most recently pinned first, rather than oldest posted. It draws none of the pin's own marks — every row here is pinned and the pane says so — so the pill, which is how a pin comes off, is the one thing it repeats from the channel. Nothing is pushed to it: a pin is the window's own record, so the list is read when it is drawn and again after anything that changes what is pinned.
- Every row of the feed is one thread as a channel draws a message: the face of whoever posted it, their name and when they posted it, what they asked as it was typed, cut at three lines with the rest waiting in the thread the row opens, and, under it, who answered — the person's own circle once they have answered, the assistant's, the count of what was said, and when it last was. The row opens on a click anywhere in it — its face, its name, its line under, its empty corner — rather than on the words alone. A row's height is settled when it is written, and nothing that happens to the thread afterwards moves it: the line under the prompt is drawn in every state — thinking, answering, needing the user, failed, answered — with the tone it wears named apart from every other block's classes, the question a row asks is drawn over the box the message keeps rather than in place of it, and a prompt's pictures are given a box each as soon as the row knows how many there were, empty until they are read.
- The composer and the transcript share one measure: a share of the window width (`72vw`), capped at `1120px`, so both grow with the window and stay in step. They also take it out of the same padding, so the composer's edges meet the message column's at every width, and both are centred on the pane they stand in. The composer's own parts — its padding, the paperclip, the send button — grow with it, so a wide window gets a composer in proportion rather than a small one adrift in a wide bar. The composer is two rows: the card the prompt is written in — the field, which is the card's whole width, riding in a box of its own that grows with what is written up to `300px` and then scrolls under it, a box of ours rather than the field's own scrolling, since a `textarea` scrolls itself and rubber-bands past its end while a box ends hard the way the transcript does, with the shortcut to send and the button that does it standing on the row's floor at the field's right end, over the strip the field keeps clear for them, so the words wrap before the button and the card's only scrollbar runs at the card's right edge — and, under the card, the row of controls that belong to the message rather than to the text: what is attached and what the chat asks for at its left, and what the chat has spent and what it is being sent with at its right. The spend is read as two amounts: the chat's whole, and, after a `+`, what its newest message added to it — the answer still arriving included, since it is being paid for as it streams. An amount that comes to nothing is left out rather than written out as `$0.00`: a chat that has spent nothing says nothing, and an answer that cost nothing adds no `+$0.00` to a total. The composer is drawn *over* the pane rather than standing under it, and the pane keeps the room for it: the bar's own height, measured as `--composer-h` on the pane, plus the air the content keeps under its last line. The surface it floats over is part of the thread's own slide rather than the bar's own paint — the bar clips what it holds, so a surface inside it would be wiped by that clip — and so the strip behind the composer travels with the pane while the composer's card stays where it is. Nothing is drawn under the bar: the room is a margin under the pane's scroller rather than padding inside it, so the scrollport itself ends where the bar begins — and the platform's scrollbar with it, rather than running down the pane's full height with its thumb cut off behind the panel. So a draft growing into a second line changes the composer and nothing else — the feed and the transcript are neither scrolled nor laid out again — and scrolled to the bottom, the last thread or message sits in that air above the bar rather than under it. The ↓ button rides above the bar on the same room.
- The model in use is named at the right of the composer's own row — beside what the chat has spent — in the app's monospace and with a chevron: clicking it opens the list of models, the one in use marked. A chat holds its own model: choosing one here saves it with that chat, and the next new chat takes up the model the most recently written chat was holding, or the head of the list when the history has nothing to say. A row written before chats had models counts as having nothing to say, so it inherits the head of the list and keeps it from then on. The name is shown whole.
- The three-dots at the right of a thread's bar opens the switches a thread has, and a bar belonging to anything else carries no menu rather than a menu with nothing in it. **JSON view** stands in for the transcript and the composer in the settings' own shape — the strip at the top, then sections down the left of the pane — and it is a mode, so that strip is where it says so: **JSON** at the strip's left, where a thread's way back stands, and the red **ESC** at its right that leaves the view (the Escape key presses it too), one bar over the pane and no second one under it. The pane is the request rather than the window's copy of it — **History** is the messages the backend assembles for the request, so the configured prompt arrives resolved, with the lazily imported servers named under it, and the timings and usage the window keeps are left out because the model is never sent them; **Tools** is the request's own tool list, grouped by the server that offers it — the app's own `load_lazy_mcp` first, offered for as long as this chat calls a lazily imported server at all — loaded or not, since the load is one-way and asking again is answered rather than unknown — each group collapsed by default and headed by how many tools it holds and what they cost a request (`11 tools ~4.3k Tok`, a token being about a quarter of the JSON sent), so a lazily imported server that has not been loaded is absent from it and appears instead as the prompt's addendum in **History** — and a **Copy** button holds the pane's bottom-right corner whatever the JSON is doing under it. The pane stays where it is, so a chat opened from the channel while the view is on shows its JSON. The view and its tab are the window's rather than any chat's: they stay on while chats are opened, until the escape button, the Escape key or `⌘J` is pressed.
- The send button holds its place whether or not there is a draft; an empty one sends nothing.
- What the chat has cost sits beside the send button: every answer's price, summed, written as money with two decimals — `$0.00`. The total is the transcript's own, summed from what each answer reported, so a chat read back from the history shows what it cost and nothing has to be kept twice, and a provider that reports no prices shows nothing at all. The answers here cost fractions of a cent, so a chat reads `$0.00` until its spend passes half a cent.
- **OpenRouter's response cache is asked for on every request** while OpenRouter is the gateway the request goes to — the app's own provider, or a gateway whose endpoint is OpenRouter's: the same request made twice — same model, same body, same key — is answered from OpenRouter's own cache the second time if it is made within five minutes, without reaching a model at all, so it is free and immediate. Every response comes back with the gateway's own verdict on it, which is kept with the answer it belongs to, so a cached one says so wherever it is read. Nothing of this goes anywhere else: a custom endpoint knows nothing of that header, and the app sends it nowhere else. Two caches are at work and they are different things: this one replays an answer whole, while the provider's own prompt cache keeps the prefix of a conversation — which the app asks no permission to use, only brings the stable prefix it needs, and reads back as a cache hit rate beside every answer's tokens. Each conversation is pinned to a single upstream with the session key OpenRouter's sticky routing takes, so the provider holding the cache is the one asked again: without that pin, routing only sticks once a hit has already happened. Providers differ in what they need, though, and the app sends what the strictest of them do: the last block of text in the request is marked with a `cache_control` breakpoint, because Gemini and Anthropic — through OpenRouter — cache nothing at all without one, while DeepSeek, OpenAI, Grok, Moonshot and Groq work the prefix out for themselves and ignore the mark. Gemini has a second rule: it writes no cache under a few thousand tokens, so a short Gemini conversation reads no cache however it is asked, while the same conversation on DeepSeek reads its share from the first turn. The two also count differently — OpenRouter hands back Gemini's prompt count with the cached tokens already added to it, so a Gemini request cached through and through reads about 50%. The rate shown is the gateway's own arithmetic on its own counters, not the app's.
- The reasoning level is chosen next to the paperclip, from **off, low, med, high**: the brain alone, in the tools' own grey, while nothing is being asked for — a click takes up `med` and turns it into a pill — and a pill of two buttons while a level is in force: the brain gives the level up, and the level's own letter and chevron open the menu, which holds off as well. Each control names itself under the pointer, the way the rail's buttons do: **Attach files** on the paperclip, **Reasoning** on the brain. The menu is drawn at the window's edge rather than in the card, whose bar clips whatever would hang out of it. The level rides with the request as the gateways' unified `reasoning.effort`, spelled out in full (`med` is `medium`), and off asks for `none` — how a model that reasons by default is told not to; a model whose reasoning is mandatory answers that with an error rather than quietly thinking. Like the model, the level belongs to the chat, is saved with it, and the next new chat takes up the level the most recently written chat was holding.
- Which model context protocol servers the chat calls is chosen beside the reasoning control, in that control's own shape and blue: the hammer alone while it calls none — and then the hammer is what opens the list, there being no other way to switch one back on — and, while it calls any, a pill of the hammer and the number of servers it calls. In that pill the hammer gives them all up and the number, with its chevron, opens the list. The list holds the servers the settings window has enabled, each with a switch that decides whether *this* conversation is sent with it, and, under its name, how many tools it offers and what they cost a request — `11 tools ~4.3k Tok`, a quarter of the JSON they are sent as, counted in the backend off the very bytes the request is charged for; a server imported lazily says `lazy` there instead — italic, and in the composer's own blue — until this chat loads it, and its count and its price from then on, like any other server's; a server that cannot be reached says so in place of both, in red, and **Refresh tools** asks them all again — connecting afresh, which is the only way to see a tool a server has grown since the window was opened. There is deliberately no way into the settings from here: what a server *is* belongs there, whether this chat calls it belongs here. The choice is saved with the chat the way its model is, so a conversation picked up again calls what it called, a new chat takes up the last one's — and every row written before there was a control for it has never chosen, which is taken as calling every enabled server.
- A tool call is one row of the transcript rather than two — and the rows of a turn are held close together and close to what they belong to, a run of them reading as one stretch of work rather than a stack of replies: how long the server took, and what was called, on a single line — in the monospace face, since it is a record of an identifier being invoked — with what the call carried left to the card rather than cut off in the row, for every tool alike, since a line of arguments in the row is a line cut off before the part worth reading and a row reading `{}` is a row reading punctuation — and the card shows what there was, `{}` included, since an empty object is the model saying it had nothing to send rather than a call that carried nothing at all. Under the pointer, or with the caret in it, the row takes the transcript's tint, its text comes up to the reading colour, and the chevron onto its card appears at the row's own end, since the whole row is what it opens. Clicking it opens that card: the server's chip and the tool, then **Arguments** and **Result**, each laid out from its JSON where it is JSON. A call and the tool message that answered it are the same fact, so they are drawn as one — paired by the id the message carries, the row read from the message that asked, since that is where the name and the arguments are written — and a call nothing has answered yet (running, or waiting on the approval card) is the same row with its timer still blank, what it carries being read in the card like any other's. The timer is the server's own time, from asking to answering: `412ms`, `0.4s`, `1:02.3`, and blank on a call that never ran — one declined, or one written before the app timed them.
- Images can be attached to a prompt: pasted into the composer, or picked through the paperclip, which opens the file panel. Each arrives as a square above the draft, drawn at once from the file and taken away again by the × at its top-right; the row scrolls sideways once there are more than fit. While an image is being prepared — decoded, and scaled down and re-encoded when it is larger than a provider comfortably takes (longest side `1600px`, JPEG) — a spinner sits over it and the send is held back, so a request never goes out missing its picture. The image rides with the prompt as an `image_url` part of its content, is drawn back in the transcript, and is kept when the answer is asked again.
- The window has no menu bar, so its commands are bound in the webview and each shortcut is shown where its command lives: `⌘,` for the settings, named on the column's row for them, and `⌘J` for the JSON view, named on the row the nav's three-dots menu holds, Escape for the way back out of whatever the pane is showing, and `⌘+Enter` to send, which the composer's placeholder says — Enter there is a newline, like any other editor's. Posting from the channel leaves the caret in the composer, so the next request can be typed without reaching for the mouse. Control stands in for Command off a Mac.
- Token-streamed assistant responses rendered as Markdown (GFM) — progressively, block by block, so each settled block is parsed once and never re-rendered. The live answer and the settled one are laid out from the same tree, so a message does not shift the moment the response ends. A list's mark is drawn by the app rather than left to the platform's own marker: the mark belongs to the item it is beside — hung in the gutter the list keeps, numbered from where the list says its numbering begins — so a selection takes it with the words and gives it up with them, and a tool's call rows, which are a list in markup only, carry no mark at all.
- Math in answers is typeset by KaTeX: `$x^2$` inline, and `$$ … $$` with the fences on their own lines for display. A formula wider than the bubble scrolls inside it, like a table.
- Your own prompts render as plain text, exactly as typed — markdown in a prompt is text, not formatting — and each is ruled off by one hand-drawn wavy line: irregular humps along a single path, so it never breaks at a repeat.
- **A thread's row in the channel offers two things under the pointer**, in a floating pill at its own top-right corner: pin the thread, or delete it. It is out of the flow, since that corner is empty — the face and the words are at the row's left — so the feed is the same height whether or not it is drawn. Pin marks the thread and the pill's icon becomes the unpin; delete asks first, twice over: the bin becomes Delete and Cancel in the pill, and the row says the same thing in its own words where the prompt was, so the row about to go is the one asking. A pinned row is drawn as a block of its own — a warm ground, a rule down its left edge, and the pin on the line its name is on — and its padding gives back what the rule takes, so every row's face, name and words stay on one column. Nothing about a row moves when it is pinned: the mark goes on a line that was already there, and the line under the prompt is held open whether or not it has anything to say, so a thread's first answer landing does not grow its row and push the ones under it down. The pin itself is a column of the row rather than part of the transcript, written on its own, so pinning a thread that is answering is not undone by what its run writes next; nothing else about the chat moves, least of all the moment it was last answered.
- A prompt under the pointer offers three things on its own head line, at that line's right-hand end, in the pill the channel's rows wear — the same component, at the same corner of the same measure: copy the message (the icon becomes a check for a moment), ask for the answer again, or rewrite it. None of them are offered while an answer is arriving, and the pill holds its place in the line whether or not a pointer is in the message — hidden rather than absent, so the transcript never moves under the pointer — which is also what keeps it off the words: the line the head is written on is as tall as the pill standing at its end, so the prompt's first line starts under both and the pill covers nothing of it. Regenerating and sending a rewrite both cut the transcript back to that prompt and start the conversation over from there: every message after it is dropped, the ones before it are untouched, and the history is rewritten the same way. Rewriting puts the message in the composer, under a line that says so and the × that gives the edit up — putting back whatever draft it displaced.
- An answer under the pointer offers its own two things in a row beneath it, hung from the answer's own left edge — a prompt's three are the pill at its corner, above: copy the message — the icon becoming a check for a moment — and, where the provider reported them, the tokens the answer used, how much of what was sent it had already cached, and what it cost. Those are a tip over the icon rather than a click: the icon is what there is to hover, and it is read, not pressed. The row is offered whenever the answer is there, whether or not the thread is answering: a run in flight is another message's business, and copying an answer is reading rather than acting — a prompt's three, which cut the transcript back and start over, are the ones that wait for the thread to be idle. Its two are set smaller than the app's own icons, being a quiet offer under a message rather than a control in a bar — and the pill wears the same size, since it is the same kind of offer at the same kind of corner. The report arrives on the stream's last frame and is kept with the answer, so a chat read back from the history still shows it; an answer written before the app kept it offers the copy alone. A response OpenRouter answered from its own cache reports no tokens and no price — every counter zeroed — so the tip names it rather than reading out the zeroes, and one whose model has no prompt cache shows no rate at all rather than a rate of nothing.
- Every answer opens with a status line: how long the model took to produce anything at all, and — only when it reasoned at all — how long it spent thinking, with a chevron onto that reasoning, both on the one line. A model that thought nothing shows the wait alone, with no zero to read and nothing to open. A turn that called tools went round several times, and what every round reasoned is gathered onto the message that answers for them — one block, its timers summed, since between them they are what the turn took — so a round that only asked for tools is left showing its call rows and nothing above them. The reasoning opens below that line, so the line under your pointer never moves, and the chevron turns down onto what it opens. The block is shut until you open it and nothing remembers your choice, so a block never opens or shuts under your hands. The line and the reasoning are chrome: neither can be selected by dragging, while the answer itself still can.
- Durations read to a tenth of a second: `0.4s`, then `12.8s`, then `1:23.4`. The wait and the thinking each carry their own.
- The transcript follows new output: while an answer streams the view is held at the lowest scroll point there is, so the newest line is the last one on screen and the only space under it is the transcript's own padding. A new message re-attaches it whatever the reader was doing — a send, or a message that arrives while nothing is streaming — since what is new is new and it is waiting at the end; scrolling up otherwise releases the follow and leaves the view where it was put, even as tokens keep arriving, and the answer landing at the end of that stream does not pull it back. That answer is not drawn twice, and never missing: the window keeps drawing the answer it has until the transcript it reads holds it as a message, so a thread is never briefly a thread without it — not for the round trip the transcript takes, and not for the seconds a tool round's calls take — and nothing is clamped out from under a reader who is reading above the end. The composer is not content either: it floats over the pane and the pane keeps its room, so a line typed into it moves nothing in the view at all, and no pass of the pin is spent on it.
- Scrolling up holds your position for as long as you read — even while tokens keep arriving — and a floating ↓ button (or scrolling back to the bottom, or sending) re-attaches.
- **Settings take the chat's place in the window** (the **Settings** row at the foot of the column, or `⌘,`), named by that row and left by it too, since a pane of the column is a pane the column names: the pane is the strip across its top — **Settings** at the strip's left, where a thread's way back stands, and the red **ESC** at its right — then a vertical list of sections down the left — **General**, **Models**, **Customization**, **MCP**, then the Logs row at its foot — opens one page beside it, that page set to a form's own measure — `640px`, under its title rather than across the pane, since a field as wide as the window is one whose beginning and end cannot be read at once; the pane has one bar and not two, since a second strip under a strip is a band of its own for a name that belongs on the first. Pressing Escape, opening a chat from the history, or starting a new chat puts them away again, and so does the column's own row for a pane: **Channel** shows the feed whether the settings were up or a thread was open over it, since a row names a pane and what it names is what shows. General holds who is posting and the scheme the window wears: where requests go and what they are sent with are the **Models** page's own, where every gateway — the app's own provider among them, its first tab — holds its key, and `provider` and `endpoint` are keys of the file rather than of this page. **Models** holds the models the picker offers: the key that pays for the models on a tab first, standing there because a gateway has to be paid for before its models are worth listing, then where that gateway is, written only when its name is not one the app knows, and then the list itself, read a gateway at a time, one tab per gateway its models are asked of, with the count of them on the tab. Above the tabs stands what a new chat starts from, **chosen from a selector** rather than read off the list — picking one moves it to the head, which is the same thing the file means by first. A model is added by typing its id — the example the field holds is one of the gateway's own, its name and slash included — and a name typed without the gateway's word before it is read with it, so what is added is the id the requests will carry either way; an id is refused while it is empty, spaced, or already listed, and one typed on the app's own provider is refused while it leads with a gateway's name — that model belongs to that gateway's tab, and the field will not pretend otherwise. The last model of the app has no bin, saying why where the bin would be. A gateway that has no tab yet is added from **Add provider** — a pill or a name of its own, the first of its models, its key, and its endpoint where the app knows no URL for the name, with the id it would write said out in full above the button before it is pressed — and gets its tab from what is then written, since a tab is a reading of the list rather than anything the file holds; a name that already leads models is refused rather than added, since adding it would move another tab's models into it. Every list in the app asks before it removes a row, and this one is no different. Customization holds the system prompt, one textarea, sent ahead of every request and never saved with a chat — the app's own note about the header each prompt carries goes under it, which is why a request carries a system message even when that box is empty. All of it lives in `~/.chalk/settings.yaml`: plaintext, and the config rather than a cache of it, so editing the file by hand is enough and editing it in the form writes the file as it is edited — a moment after the last edit, and at once when the window loses the focus or the settings are left, since every field here is a fact about the file rather than a form under review, so there is no Save to press; the MCP page is the one that keeps a Save, its servers being a list added to and tried one at a time. The list's order is the picker's order, and its first entry is what a chat starts from when the history has nothing to say; a file still holding the single `model` key this settings file began with reads as a list of one, and a row left blank is not a model — it is dropped when the file is read. `provider` is one of two names — `openrouter`, or `custom`, which sends to the `endpoint` beside it — and a file written the old way, naming a gateway or spelling the endpoint out, is read into that pair: a name this app then knew — `openai`, `google`, `deepseek`, `groq`, `mistral`, `xai`, `ollama`, `lmstudio` — becomes the endpoint it stood for, and OpenRouter's own URL is read as OpenRouter, which is what asks for its cache. `gateways` is the other half of that: the services a model may be asked of by name — each an `id`, the word its models' ids lead with, an `endpoint` written only where the app knows no URL for the name, and a key of its own. A model whose id leads with a configured gateway's name is asked of that gateway, with that gateway's key; every other one — OpenRouter's own vendor-prefixed ids included, and the ids that lead with nothing — is asked of the app's provider. That is what keeps an Anthropic model served by OpenRouter on OpenRouter: `anthropic/claude-sonnet-4.5` names the model, not the way to reach it, and only an `anthropic` gateway makes it mean otherwise. Any OpenAI-compatible service works, as a custom provider or as a gateway of its own. The file is generated rather than hand-maintained: a rewrite keeps its own keys and drops comments and anything else in it. The first run after the move carries over whatever `config.json` in the OS app-config directory held, so the key already in use is not lost to it. Saving updates the model chip. The API key is shown while the field has the caret and masked the rest of the time — its first five characters, then one asterisk per character after them — so it can be read and corrected in place, while a glance at an unfocused window, or a copy of the field, gives away nothing past the fifth. The button at the foot of the sections opens the log window.
- **Model context protocol servers** are configured in the settings' **MCP** page and kept in `~/.chalk/mcp.json`, beside the settings and as hand-editable: the file is the config rather than a cache of it, and it is kept to its owner's read, since a server's headers are where a key goes. A server is reached either by running a program and speaking the protocol over its standard streams (**stdio**) or by posting each message to a URL (**streamable HTTP**, with whatever headers the server needs); the page is two columns — the servers down the left, at the width of the sections beside them, and the open one to the right of a rule — where **New server** at the head of the list opens an empty form and a row opens the one it names, saying in passing when it is switched off. The form reads in three parts. **Connection** is how the app reaches the server: the two transports as the cards that choose between them — a **Remote server**, reached at a URL, for the services you sign in to, and a **Local program**, a command started on this computer and spoken to over its streams — and then the field the chosen one is addressed by, the URL or the command and its arguments. **Details** is what the server is called and what the model is told about it: the name and the ID it is named by in the names the model is given, the two written on one line since they are one answer read twice — `<id>__<tool>`, so the ID is one word, and it follows the name until it is typed into by hand — and then the description a lazy server is known by, since that is all the model sees of it until it loads the tools. **Behaviour** is whether the server is offered at all and whether its tools are held back for the model to ask for with `load_lazy_mcp`. The connection is tried where it is written: the box under the headers says what there is to test and what came of it — nothing to reach it by yet, ready, being asked, answered, or refused with what the backend said — and holds the button that asks, with what the server answers read under it: the revision it agreed on, what it calls itself, and the tools it offers, saved or not. A server enters the file when the button on the form's own head line is pressed — **Add server** for one that is not in it yet, **Save** for one that is — and the receipt beside it, before it rather than after, says what was written: the button holds the form's own right-hand edge, so the word coming and going moves nothing, and it rides the head rather than the foot because the form is read from the top and is taller than the column it stands in, so the one control that writes the whole of it is not something to be found by scrolling to the end of it. A test writes nothing, saved or not. A row is removed by the bin at its end, which asks the same question the history's rows ask, and the removal is written there and then. A server that is off is never started and its tools are never offered. What a request carries is the tools of the servers the *chat* calls — switched one at a time in the composer, and every enabled server until something is switched — and a call is carried out in the backend over the connection the app already holds; a server marked `"lazy": true` holds its tools back instead: they are not in the request at all, and what the model is given is its name, its `description` and the names of the tools it holds — no definitions, which is what the laziness is saving — in the system prompt under `Lazy Imported MCPs`, with a `load_lazy_mcp` tool to ask for the rest by. Calling that with a server's name puts its tools into the conversation like any other server's, and there they stay for the rest of the thread: the load is one-way, so a tool that has answered is never taken away under the model's hands; the result goes back as the `tool` message the conversation continues from. A server's tools run as the model asks for them unless the file says `"autoRun": false` on it — the one place that is decided, and never a control in the window — and then its calls stop above the composer until they are allowed or declined, either answer going back as the call's result. A tool the server itself declares read-only is the exception: it runs as the model asks either way, because the protocol's own hint says it changes nothing, so a round that only reads goes through while a round with a write in it stops. A file that does not mention the key at all runs them: the protocol asks hosts to obtain consent, and a server that is declared is taken as one its owner has decided about. One turn may go round for tools eight times before it is stopped — the calls of that last round are answered anyway, since a call left unanswered is one the provider refuses.
- **The app manages itself, too**: eight tools of its own ride with every request — `models_list`, `model_add`, `model_remove`, `mcp_list`, `mcp_add`, `mcp_update`, `mcp_remove`, `mcp_test`. They are offered the way a server's are and answered the way its settings window answers, and the JSON view groups them under **Chalk** beside the loader; what sets them apart is that no server is on them, so their rows in the transcript read as the tool alone — no separator, and no chip on the card — where a server's call reads as the server, the separator and the tool. They are in every request rather than a chat's choice — not something a chat can switch off — and they run as the model asks rather than stopping for an Allow, so what they did is a row of the transcript either way. What they write is exactly what the settings window writes: `settings.yaml` for the models and `mcp.json` for the servers, through the same save path, so a model that declares a server has it reachable on the next request and one that adds a model has it in the picker. The settings' own rules come with them: an id is added once, a place that is not there is refused, the last model cannot be removed, and a server is one word with something to reach it by. Two things they never touch — the API key, which would then be in the transcript and in the model's context, and the provider with its endpoint. A bearer token in a server's headers is named by its key and never by its value: `mcp_list` says which headers a server is reached with, not what is in them, so a listing can be read out loud.
- The protocol client speaks the two revisions this app is written for: `2026-07-28`, where there is no handshake at all and every request carries its own version, capabilities and identity, and `2025-11-25`, where a session is opened with an `initialize` first. A server is probed with the newer revision and falls back to the older one, so a server of either era works and the newer is used when both are on offer. The framing, the two transports and the negotiation are the reference Rust implementation's (`rmcp`), not this app's: what is here is the configuration, the connections, and the names the model sees. A server's own stderr is read into the log window, which is where a server that will not start says why.
- **The log is a window of its own** (Settings → the Logs row at its foot), declared in `tauri.conf.json` and rebuilt from that declaration if it has been closed, so it can be left open beside the chat. It shows the backend's entries, backfilled from `get_logs` and followed live over `app-log`, plus the log window's own console output; no other window's console is collected.
- All HTTP runs in the Rust backend via `reqwest`, and streaming is delivered to the webview over a Tauri `Channel`. The API key never reaches the webview, and there is no CORS involvement, so any OpenAI-compatible endpoint works.

Type is set in Space Grotesk (display), DM Sans (UI), and Newsreader (message text), the last at one size wherever the chat's own words are written — a prompt in the feed, the question a row asks in its place, a message in the transcript, and the draft in the composer, which is those words on their way in — so what is typed and what it becomes are set alike. Bundled with the app so nothing is fetched at runtime. The window's scheme is a choice of its own — light, dark, or the desktop's own, which is the default — set in Settings under General, applied as it is made, and kept for the window rather than in the settings file the form writes.

**The controls are drawn once**, in `src/styles/components.css`: the buttons (`btn` with `--primary`, `--secondary`, `--subtle`, `--quiet`, `--ghost`, `--dashed`, `--pill`, `--danger`, at the sizes a form, a card, a row and a bar need), the composer's pills, the segmented set a choice of a few is made in — which is also what a strip of tabs is, the same track with `aria-selected` instead of `aria-pressed` — the fields — the platform's own `input`, `select` and `textarea`, dressed rather than rebuilt, and the secret field two pages hold the key in, masked away from the caret — the menus and tips, and the nav rows. Each is a plain element with a class, so a feature's sheet keeps only what is its own business: where a thing stands, how wide it is, and the words on it. A control's colour, radius, type and states live in one place, which is why the same dark button is written once rather than once per feature. Icons are Lucide at 16 px with a 1.5 stroke — one rule over the whole app, `svg.lucide` — and the app's depth is one token, `--shadow-menu`, worn by what floats over a pane.

## Transparency and the App Store

A transparent window on macOS needs Tauri's `macos-private-api` feature (`Cargo.toml`) and `app.macOSPrivateApi` (`tauri.conf.json`). That is what makes the rounded corners possible, and it uses private APIs — **an App Store submission would have to drop the transparency**, and with it the rounded corners.

## Prerequisites

- Node.js (for npm)
- Rust (stable toolchain)
- macOS, Windows, or Linux desktop

## Run

```sh
npm install
npm run tauri dev
```

This starts Vite and compiles the Rust backend, then opens the desktop window.

Open **Settings** to edit the provider, the key, the models, or the system prompt — they are written to `~/.chalk/settings.yaml` as you edit them, a moment after the last keystroke and at once when the window loses the focus, so there is no Save to press, and they apply from the next request on. Its **Models** page holds the key and the list together, a tab per gateway: the **Add provider** screen offers the two arrangements of that provider — **OpenRouter**, and **OpenAI Compatible** for a model server of your own or any other endpoint that speaks this API, which is the one that asks for its base URL; an arrangement that is already set up is not offered again, its key and its models being read on the tab it already has, and only an OpenAI-compatible endpoint is started over and over, since the same word may be pointed somewhere else — while every other tab is a gateway a hand-edited file declares, which keeps its own key and its own tab under its own name. A model whose id names no gateway is asked of the app's own provider, which is how a self-hosted model rides the same list as a cloud one; what a new chat starts from is chosen on that page too, without moving the model in the list; its **MCP** page adds model context protocol servers, which are saved to `~/.chalk/mcp.json`: either a program to run and speak to over its standard streams, or a URL to post to, with the headers it needs. Their tools are offered to the model and run as it asks for them; a server marked `"autoRun": false` in that file has its calls stop for you to allow instead, and one marked `"lazy": true` is not offered at all until the model loads it by name. The chat history is `chats.db` in the OS app-data directory; deleting it starts the history over, and the app runs without history at all if it cannot be opened.

Defaults point at OpenRouter: `provider: openrouter`, a list of one model, `deepseek/deepseek-v4.1-flash`, that model named again in `default_model` — what a new chat starts from is a model rather than the head of the list, so choosing another never reorders the picker — and no key — the app ships without one, so add yours in Settings or in the file before the first request. A file that names another gateway, or writes an endpoint out by hand, is read as `provider: custom` with that endpoint in `endpoint`, and saving from Settings writes the file the new way; OpenRouter's own URL written out is read as OpenRouter, since the name is what its cache hangs off.

## Build a release bundle

```sh
APPLE_SIGNING_IDENTITY="-" npm run tauri build -- --target aarch64-apple-darwin
```

The signing identity is not optional: without it the bundle carries only the
linker's ad-hoc signature and macOS reports it as damaged rather than as an
app from an unidentified developer. [`skills/RELEASE.md`](skills/RELEASE.md)
has the whole release — the version bump, the secret check, the artifact
verification, and the published dmg.
