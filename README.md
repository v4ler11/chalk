# Chalk

A desktop chat client for any OpenAI-compatible API, built with Tauri 2 (Rust backend) + React + TypeScript + Vite.

The interface follows the design the app was built from: a frameless window whose chrome is drawn in the webview, a conversation sidebar, a serif reading column for the transcript, and a rounded composer card.

- Chat history in SQLite: one row per chat, holding the whole transcript as JSON — the same array the UI holds, its timing keys and the provider-shaped payloads included — in `chats.db` in the OS app-data directory. The sidebar lists the chats most recently written first, grouped by calendar day; a row opens its chat on a click, renames it in place on a double click, and deletes it — after asking, and from the button that appears under the pointer. The most recently written chat is reopened at launch.
- A chat enters the history with its first message, so **New chat** is a draft with no row of its own, and is written again as each message settles: a reload, a crash, or a quit mid-answer keeps everything up to the last message. A chat is named after its first prompt, and a rename replaces that name. Writing is chained, since a transcript is stored whole and an older write landing last would put the older transcript back.
- A system prompt can be set in the settings window. It is prepended to every request as a `system` message there, in the backend, rather than held by the window: a chat's transcript never carries it, and changing it applies from the next request on. The prompt may hold `@{{TODAY}}`, which is replaced on each send with that send's date and time in the user's own time zone — `Fri 2 Oct 2026 20:39:02`. The file keeps the prompt as written, so the token stays live; a name the app does not know is left as written rather than being eaten. Nothing searches the history yet. Token counts and price are kept with the answer they were reported for, so a transcript carries them back with it.
- Frameless window (`decorations: false`), transparent so its corners are the app's own (`border-radius`) rather than the OS's. The window is a row: the sidebar's own column on the left, and the chat panel taking everything else, from the window's top edge to its bottom. Each panel carries its own head: the sidebar's is the window's chrome — the traffic lights, which drive the real window, and the sidebar and New chat buttons — while the chat panel has a nav strip naming the model in use, ruled off from the transcript below it. Both heads are drag regions, so a press anywhere along the top moves the window and a double-click maximizes, while the controls and the model chip keep their own clicks. Open, the chrome sits on the sidebar's head, sharing its colour, its right edge continuing the sidebar's border; shut, it takes only the width of its controls and wears the chat panel's colour, so it costs the panel no width and the panel — with the composer centred in it — runs the full window.
- The sidebar slides out of its column's left edge when it opens and back in when it closes, and stays mounted either way so there is something to slide.
- Every chat row is marked with its own wave: a stroke whose humps vary in width and amplitude, derived from the row's title, so the history reads as different conversations rather than one stamp repeated.
- The composer and the transcript share one measure: a share of the window width (`72vw`), capped at `1120px`, so both grow with the window and stay in step. They also take it out of the same padding, so the composer's edges meet the message column's at every width, and both are centred on the chat panel — the window while the sidebar is shut, and what the sidebar leaves while it is open. The composer's own parts — the draft's type, its padding, the paperclip, the send button — grow with it, so a wide window gets a composer in proportion rather than a small one adrift in a wide bar.
- The model in use is named at the right of the chat panel's nav, with a chevron: clicking it opens the list of models, the one in use marked. A chat holds its own model: choosing one here saves it with that chat, and the next new chat takes up the model the most recently written chat was holding, or the head of the list when the history has nothing to say. A row written before chats had models counts as having nothing to say, so it inherits the head of the list and keeps it from then on. The name is shown whole.
- The send button holds its place whether or not there is a draft; an empty one sends nothing.
- What the chat has cost sits beside the send button: every answer's price, summed, written as money with two decimals — `$0.00`. The total is the transcript's own, summed from what each answer reported, so a chat read back from the history shows what it cost and nothing has to be kept twice, and a provider that reports no prices shows nothing at all. The answers here cost fractions of a cent, so a chat reads `$0.00` until its spend passes half a cent.
- The reasoning level is chosen next to the paperclip, from **off, low, med, high**: the brain alone, in the tools' own grey, while nothing is being asked for — a click takes up `med` and turns it into a pill — and a pill of two buttons while a level is in force: the brain gives the level up, and the level's own letter and chevron open the menu, which holds off as well. Each control names itself under the pointer, the way the rail's buttons do: **Attach files** on the paperclip, **Reasoning** on the brain. The menu is drawn at the window's edge rather than in the card, whose bar clips whatever would hang out of it. The level rides with the request as the gateways' unified `reasoning.effort`, spelled out in full (`med` is `medium`), and off asks for `none` — how a model that reasons by default is told not to; a model whose reasoning is mandatory answers that with an error rather than quietly thinking. Like the model, the level belongs to the chat, is saved with it, and the next new chat takes up the level the most recently written chat was holding.
- Which model context protocol servers the chat calls is chosen beside the reasoning control, in that control's own shape and blue: the hammer alone while it calls none — and then the hammer is what opens the list, there being no other way to switch one back on — and, while it calls any, a pill of the hammer and the number of servers it calls. In that pill the hammer gives them all up and the number, with its chevron, opens the list. The list holds the servers the settings window has enabled, each with a switch that decides whether *this* conversation is sent with it, and, under its name, how many tools it offers and what they cost a request — `11 tools ~4.3k Tok`, a quarter of the JSON they are sent as, counted in the backend off the very bytes the request is charged for; a server imported lazily says `lazy` there instead — italic, and in the composer's own blue — until this chat loads it, and its count and its price from then on, like any other server's; a server that cannot be reached says so in place of both, in red, and **Refresh tools** asks them all again — connecting afresh, which is the only way to see a tool a server has grown since the window was opened. There is deliberately no way into the settings from here: what a server *is* belongs there, whether this chat calls it belongs here. The choice is saved with the chat the way its model is, so a conversation picked up again calls what it called, a new chat takes up the last one's — and every row written before there was a control for it has never chosen, which is taken as calling every enabled server.
- A tool call is one row of the transcript rather than two — and the rows of a turn are held close together and close to what they belong to, a run of them reading as one stretch of work rather than a stack of replies: how long the server took, what was called, and the arguments as they were sent, on a single line, cut off rather than wrapped — in the monospace face, since it is a record of an identifier being invoked. Under the pointer, or with the caret in it, the row takes the transcript's tint, its text comes up to the reading colour, and the chevron onto its card appears. Clicking it opens that card: the server's chip and the tool, then **Arguments** and **Result**, each laid out from its JSON where it is JSON. A call and the tool message that answered it are the same fact, so they are drawn as one — paired by the id the message carries, the row read from the message that asked, since that is where the name and the arguments are written — and a call nothing has answered yet (running, or waiting on the approval card) shows its arguments alone. The timer is the server's own time, from asking to answering: `412ms`, `0.4s`, `1:02.3`, and blank on a call that never ran — one declined, or one written before the app timed them.
- Images can be attached to a prompt: pasted into the composer, or picked through the paperclip, which opens the file panel. Each arrives as a square above the draft, drawn at once from the file and taken away again by the × at its top-right; the row scrolls sideways once there are more than fit. While an image is being prepared — decoded, and scaled down and re-encoded when it is larger than a provider comfortably takes (longest side `1600px`, JPEG) — a spinner sits over it and the send is held back, so a request never goes out missing its picture. The image rides with the prompt as an `image_url` part of its content, is drawn back in the transcript, and is kept when the answer is asked again.
- The window has no menu bar, so its commands are bound in the webview and each shortcut is shown where its command lives: `⌘N` for a new chat and `⌘B` for the sidebar, named under their buttons in the rail, `⌘,` for the settings window, named on the sidebar's Settings row, and `⌘+Enter` to send, which the composer's placeholder says — Enter there is a newline, like any other editor's. A new chat leaves the caret in the composer, so the next request can be typed without reaching for the mouse. Control stands in for Command off a Mac.
- Token-streamed assistant responses rendered as Markdown (GFM) — progressively, block by block, so each settled block is parsed once and never re-rendered. The live answer and the settled one are laid out from the same tree, so a message does not shift the moment the response ends.
- Math in answers is typeset by KaTeX: `$x^2$` inline, and `$$ … $$` with the fences on their own lines for display. A formula wider than the bubble scrolls inside it, like a table.
- Your own prompts render as plain text, exactly as typed — markdown in a prompt is text, not formatting — and each is ruled off by one hand-drawn wavy line: irregular humps along a single path, so it never breaks at a repeat.
- A prompt under the pointer offers three things beneath it, in the gap the transcript already leaves: copy the message (the icon becomes a check for a moment), ask for the answer again, or rewrite it. None of them are offered while an answer is arriving, and the row holds no space, so the transcript never moves under the pointer. Regenerating and sending a rewrite both cut the transcript back to that prompt and start the conversation over from there: every message after it is dropped, the ones before it are untouched, and the history is rewritten the same way. Rewriting puts the message in the composer, under a line that says so and the × that gives the edit up — putting back whatever draft it displaced.
- An answer under the pointer offers its own two things in the same row beneath it, hung from the answer's own left edge the way a prompt's hang from the right: copy the message — the icon becoming a check for a moment — and, where the provider reported them, the tokens the answer used and what it cost. Those are a tip over the icon rather than a click: the icon is what there is to hover, and it is read, not pressed. The report arrives on the stream's last frame and is kept with the answer, so a chat read back from the history still shows it; an answer written before the app kept it offers the copy alone.
- Every answer opens with a status line: how long the model took to produce anything at all, and — only when it reasoned at all — how long it spent thinking, with a chevron onto that reasoning, both on the one line. A model that thought nothing shows the wait alone, with no zero to read and nothing to open. A turn that called tools went round several times, and what every round reasoned is gathered onto the message that answers for them — one block, its timers summed, since between them they are what the turn took — so a round that only asked for tools is left showing its call rows and nothing above them. The reasoning opens below that line, so the line under your pointer never moves, and the chevron turns down onto what it opens. The block is shut until you open it and nothing remembers your choice, so a block never opens or shuts under your hands. The line and the reasoning are chrome: neither can be selected by dragging, while the answer itself still can.
- Durations read to a tenth of a second: `0.4s`, then `12.8s`, then `1:23.4`. The wait and the thinking each carry their own.
- The transcript follows new output: while an answer streams the view is held at the lowest scroll point there is, so the newest line is the last one on screen and the only space under it is the transcript's own padding. A new message re-attaches it whatever the reader was doing — a send, or a message that arrives while nothing is streaming — since what is new is new and it is waiting at the end; scrolling up otherwise releases the follow and leaves the view where it was put, even as tokens keep arriving, and the answer landing at the end of that stream does not pull it back.
- Scrolling up holds your position for as long as you read — even while tokens keep arriving — and a floating ↓ button (or scrolling back to the bottom, or sending) re-attaches.
- **Settings is a separate window** (sidebar → Settings), divided by a sidebar of its own into **General**, **Customization** and **MCP**. General holds the runtime-editable provider, bearer key, and models — a list, added to and removed from a row at a time, that cannot be emptied. Customization holds the system prompt, one textarea, sent ahead of every request and never saved with a chat. All four live in `~/.chalk/settings.yaml`: plaintext, and the config rather than a cache of it, so editing the file by hand is enough and editing it in the window rewrites the file there and then. The list's order is the picker's order, and its first entry is what a chat starts from when the history has nothing to say; a file still holding the single `model` key this settings file began with reads as a list of one, and a row left blank is not a model — it is dropped when the file is read. `provider` is a name or an endpoint — `openrouter`, `openai`, `deepseek`, `groq`, `ollama` and `lmstudio` are known, and anything else is used as the endpoint itself, so any OpenAI-compatible service works without the list growing. The file is generated rather than hand-maintained: a rewrite keeps its four keys and drops comments and anything else in it. The first run after the move carries over whatever `config.json` in the OS app-config directory held, so the key already in use is not lost to it. It is declared in `tauri.conf.json` and rebuilt from that declaration if it has been closed. Saving there updates the model chip. The API key is shown while the field has the caret and masked the rest of the time — its first five characters, then one asterisk per character after them — so it can be read and corrected in place, while a glance at an unfocused window, or a copy of the field, gives away nothing past the fifth. The button at the foot of the sections opens the log window.
- **Model context protocol servers** are configured in the settings window's **MCP** page and kept in `~/.chalk/mcp.json`, beside the settings and as hand-editable: the file is the config rather than a cache of it, and it is kept to its owner's read, since a server's headers are where a key goes. A server is reached either by running a program and speaking the protocol over its standard streams (**stdio**) or by posting each message to a URL (**streamable HTTP**, with whatever headers the server needs); the page lists the servers, edits one at a time — type, name, id, url or command, headers or environment, and, for a server held back rather than offered, its **Import lazily** switch and the description the model reads in place of its tools — and can **Test** a server, saved or not, which connects, shows the revision that was agreed on, what the server calls itself, and the tools it offers. The id names the server in the names the model is given — `<id>__<tool>` — so it is held to one word. A server enters the list when it is saved, not when it is started on; a row is removed by the bin at its end, which asks the same question the history's rows ask, and the removal is written there and then. A server that is off is never started and its tools are never offered. What a request carries is the tools of the servers the *chat* calls — switched one at a time in the composer, and every enabled server until something is switched — and a call is carried out in the backend over the connection the app already holds; a server marked `"lazy": true` holds its tools back instead: they are not in the request at all, and what the model is given is its name, its `description` and the names of the tools it holds — no definitions, which is what the laziness is saving — in the system prompt under `Lazy Imported MCPs`, with a `load_lazy_mcp` tool to ask for the rest by. Calling that with a server's name puts its tools into the conversation like any other server's, and there they stay for the rest of the thread: the load is one-way, so a tool that has answered is never taken away under the model's hands; the result goes back as the `tool` message the conversation continues from. A server's tools run as the model asks for them unless the file says `"autoRun": false` on it — the one place that is decided, and never a control in the window — and then its calls stop above the composer until they are allowed or declined, either answer going back as the call's result. A file that does not mention the key at all runs them: the protocol asks hosts to obtain consent, and a server that is declared is taken as one its owner has decided about. One turn may go round for tools eight times before it is stopped — the calls of that last round are answered anyway, since a call left unanswered is one the provider refuses.
- The protocol client speaks the two revisions this app is written for: `2026-07-28`, where there is no handshake at all and every request carries its own version, capabilities and identity, and `2025-11-25`, where a session is opened with an `initialize` first. A server is probed with the newer revision and falls back to the older one, so a server of either era works and the newer is used when both are on offer. The framing, the two transports and the negotiation are the reference Rust implementation's (`rmcp`), not this app's: what is here is the configuration, the connections, and the names the model sees. A server's own stderr is read into the log window, which is where a server that will not start says why.
- **The log is a window of its own** (Settings → its sidebar's Logs row), declared in `tauri.conf.json` and rebuilt from that declaration if it has been closed, so it can be left open beside the chat. It shows the backend's entries, backfilled from `get_logs` and followed live over `app-log`, plus the log window's own console output; no other window's console is collected.
- All HTTP runs in the Rust backend via `reqwest`, and streaming is delivered to the webview over a Tauri `Channel`. The API key never reaches the webview, and there is no CORS involvement, so any OpenAI-compatible endpoint works.

Type is set in Space Grotesk (display), DM Sans (UI), and Newsreader (message text), bundled with the app so nothing is fetched at runtime. Both the light theme and the OS dark scheme are supported.

## Transparency and the App Store

A transparent window on macOS needs Tauri's `macos-private-api` feature (`Cargo.toml`) and `app.macOSPrivateApi` (`tauri.conf.json`). That is what makes the rounded corners possible, and it uses private APIs — **an App Store submission would have to drop the transparency**, and with it the rounded corners.

## Prerequisites

- Node.js (for npm)
- Rust (stable toolchain)
- macOS, Windows, or Linux desktop

## Run

```sh
npm install
npm run tauri dev
```

This starts Vite and compiles the Rust backend, then opens the desktop window.

Open **Settings** to edit the provider, API key, the list of models, or the system prompt — they are saved to `~/.chalk/settings.yaml` and apply from the next request on — and its **MCP** page to add model context protocol servers, which are saved to `~/.chalk/mcp.json`: either a program to run and speak to over its standard streams, or a URL to post to, with the headers it needs. Their tools are offered to the model and run as it asks for them; a server marked `"autoRun": false` in that file has its calls stop for you to allow instead, and one marked `"lazy": true` is not offered at all until the model loads it by name. The chat history is `chats.db` in the OS app-data directory; deleting it starts the history over, and the app runs without history at all if it cannot be opened.

Defaults point at OpenRouter: `provider: openrouter`, a list of one model, `deepseek/deepseek-v4.1-flash`, and no key — the app ships without one, so add yours in Settings or in the file before the first request.

## Build a release bundle

```sh
APPLE_SIGNING_IDENTITY="-" npm run tauri build -- --target aarch64-apple-darwin
```

The signing identity is not optional: without it the bundle carries only the
linker's ad-hoc signature and macOS reports it as damaged rather than as an
app from an unidentified developer. [`skills/RELEASE.md`](skills/RELEASE.md)
has the whole release — the version bump, the secret check, the artifact
verification, and the published dmg.
